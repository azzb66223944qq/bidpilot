## 一、商机雷达 BidRadar

### 1.0 核心架构（关键洞察：匹配在本地，只有公开数据在流动）

```
GitHub Actions 定时任务(每日)                 经销商浏览器(PWA, 本地)
  ├─ 抓取公开公告(ccgp/省级平台)                ├─ 拉取 announce-feed.json(公开数据)
  ├─ 只做"提取+去重+分类"                       ├─ 载入本机设备库(永不上传)
  └─ 提交 announce-feed.json 到仓库    ──────▶  └─ 本地批量匹配 → "今天你能投的3个标"
        (GitHub Pages 免费托管)                        就绪度预评分 · 一键载入完整分析
```

铁律保持：**设备库、词库、历史——一切客户数据留在本机；流动的只有公开公告**。
答辩话术："我们连商机匹配都在客户电脑上做，平台只分发公开信息。"

### 2.0 模块设计（文件级）

**engine.js 新增（纯函数，延续可测试性）：**
- `buildDeviceFingerprint(libText)` → 从设备库提取参数向量 `{paramId: {value, unit, normalized}}`（复用 extractNum/PARAM_DEFS，等于 collectParams 的资料库版）
- `triageAnnouncement(fp, tenderText)` → 轻量预筛：★硬过滤（负偏离即"不可投"）+ 参数覆盖率 → 返回 `{verdict: '可投'|'边缘'|'不可投', coverage, kills[], gaps[]}`（不跑完整 analyze，单标<5ms）
- `matchFeed(fps, feed)` → N台设备 × M条公告的批量矩阵，输出排序清单
- 对应测试：批量矩阵正确性、★硬过滤、覆盖率排序（延续142项断言体系）

**index.html 新增：**
- "📡 商机雷达"标签页：设备库多选 → 拉取feed → 匹配表格（公告/机型/预判/差距/操作）
- 每条"一键载入"→ 现有完整分析流程
- feed 更新指示（sw.js 网络优先策略已支持）

**仓库新增：**
- `.github/workflows/radar.yml`：每日 cron，抓取→提取→commit JSON
- `feed/announce-feed.json`：`[{id, title, region, deadline, source, url, tenderText, fetchedAt}]`

### 3.0 三阶段里程碑

| 阶段 | 周期 | 交付 | 验证目标 |
|---|---|---|---|
| P1 批量模式（零新基建） | 2周 | 多公告粘贴/多PDF导入 → 批量对比表 | 试点经销商愿不愿意每天用；匹配准确率 |
| P2 自动feed | 4-6周 | Actions定时采集ccgp工程机械品类 → 每日清单 | 日活、误报率（"可投"里真可投的比例） |
| P3 闭环校准 | 之后 | 用户标记"投了/没投/中了"（本机）→ 权重回调 → 中标率校准（衔接梯队二） | 预测命中率 |

### 4.0 风险与合规（必须提前想清）
1. **口径更新**：Defense-QA Q4 原说"不依赖爬虫"——需改为"不碰客户数据；公告采集仅限依法公开的政府采购信息，遵守robots与访问频率，仅存储原文链接与结构化要素"。这条要在材料里同步。
2. **公告版权**：只存结构化要素+原文链接+必要摘录，不整篇转载。
3. **抓取稳定性**：政府站点改版风险 → P2设计"源失败降级"（feed缺失时P1手工模式依然可用）。
4. **误报治理**："可投"误报伤信任 → 保守策略：宁漏勿误，边缘标一律标"待人工核实"。

## 二、废标判例库

### 1.0 数据源（全部依法公开）
- 中国政府采购网 + 各省财政厅：**投诉处理决定/行政处罚公告**（每省都有公开栏目）
- 财政部政府采购指导性案例（已结集公开）
- 湖南等省"评审专家常见错误案例"系列（本次调研发现）
- 各地公共资源交易中心：异常投标行为公示、失信记录
- （远期）中国裁判文书网：招标投标纠纷判决

### 2.0 数据结构（schema）

```json
{
  "id": "case-2026-001",
  "title": "某装载机采购项目投诉处理决定",
  "authority": "XX省财政厅",
  "date": "2026-03",
  "stage": "资格审查|符合性审查|评标|开标",
  "category": "保证金|解密超时|授权书|★参数|串标|资质|格式|报价",
  "outcome": "投标无效|废标|投诉成立|行政处罚",
  "basis": "《政府采购法》第XX条 / 招标文件第X章",
  "quote": "……（原文关键句，不改写）",
  "url": "官方原文链接"
}
```

### 3.0 引用协议（反幻觉纪律的延续）
- 判例**只存原文引用+官方链接**，摘要句与原文用引号明确区分；
- engine.js 的 `buildRisks()` 每条风险按 `category` 挂载判例引用：`[{title, authority, quote, url}]`；
- 报告渲染："保证金三查 ⚖ 已有同类判例：XX省财政厅2026年X月认定……（原文摘录）[链接]"；
- 没有判例的风险条目诚实显示"暂无同类判例"——延续"宁可不判定，不可错判定"。

### 4.0 冷启动与规模化
- **冷启动（队友可执行，复用品类样本收集SOP的作业模式）**：按 category × stage 矩阵手工整理 50-100 条精选判例，每条带链接核验——两周量级，正好是招募队员的实战任务；
- **规模化**：GitHub Actions 定时采集各省公开栏目 → 结构化抽取（确定性规则优先，LLM仅做初分类、人工抽检）→ 判例 JSON 入库；
- **资产化**：判例库成为不可复制的数据墙（别人要重新踩一遍采集+核验的坑）。

### 5.0 里程碑
| 阶段 | 周期 | 交付 |
|---|---|---|
| J1 手工50条 | 2周 | 判例JSON + buildRisks 引用渲染 + 测试 |
| J2 采集管线 | 4-6周 | 定时采集3-5个省源，月增100+条 |
| J3 覆盖率 | 持续 | 按"风险类别覆盖率达80%"运营 |

## 三、协同与顺序建议

1→2 而非并行：先 BidRadar P1（纯引擎批量化，2周可见效、试点可验证），同期队友做判例库 J1（手工为主不冲突）；BidRadar P2 与判例库 J2 同为"采集管线"，技术复用（同一套 Actions 采集框架）。

**与195号文的对表**：BidRadar≈"智能商机发现"，判例库≈"招标文件检测"的民间版——答辩时每项升级都能挂到政策条目上。
